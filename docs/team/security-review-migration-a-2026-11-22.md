## Medium

### MA1. Admins skip the document guard because `private.is_trusted()` is true for them
Where: migration lines 252-311 (`private.guard_person_document`), and line 385 (`private.guard_person_check`). `private.is_trusted()` (`20261012000100_private_helpers.sql` line 16) is `current_user not in ('anon','authenticated') or private.is_admin()`. The comment on line 251 assumes it only sees "the real caller"; for an `aal2` admin it is true.
Abuse: an admin inserting into `person_documents` directly (they hold the same column insert grant as everyone) skips the provider ownership check, the "file exists" check and the 30-document cap. RLS still forces `user_id = auth.uid()` and the column grants keep `review_state` at its default, but the admin can attach a document row to someone else's business (`provider_id`) with a path to a file that does not exist or to their own file. A second admin accepting it creates a business check for a business the uploader does not own. Insider abuse, needs two admins, but it defeats the M2 guard.
Fix for tech-lead: in both new guards test the role only, `if current_user in ('anon', 'authenticated') then ... end if;` (definer functions and service_role still pass; admins calling from the client do not). Keep `private.is_trusted()` for older tables. Add SQL tests: an `aal2` admin inserting a business document for a provider they do not own is refused, and an insert with no file is refused.

### MA2. The read-limit alert to admins is rolled back and never sent
Where: lines 940-950 (`public.svc_identifier_cipher_for_read`). `private.notify_user(...)` inserts into `notification_outbox`, then `raise exception 'rate_limited'` aborts the transaction, which removes the outbox rows. The "once per hour" lookup therefore also never finds a row.
Harm: the M4 requirement "an email alert to Walter above that" is not met. An admin (or a stolen admin session) hitting the limit is refused silently; nobody is told.
Fix: do not raise after notifying. Return a result instead (for example `returns jsonb` with `{"error":"rate_limited"}` or `{"cipher":"..."}`), so the notification commits; the Edge Function maps the error to 429. Also log the refused attempt in `person_check_log` (new action, for example `identifier_read_refused`). SQL test: the 21st read in an hour leaves exactly one `identifier_read_limit` email row per admin in the outbox.

### MA3. The sweep deletes ID files with no brake and no dry run
Where: `public.svc_verification_sweep_list` (lines 977-1020) and `supabase/functions/verification-sweep/index.ts` lines 38-65.
Risk: the `no_account` and `no_row` rules delete every object they cannot match to a `profiles` row, a `person_documents` row or a legacy `guide_private` / `provider_private` path. Any mistake in those lookups (a later rename of a legacy column, a new table that stores `verification` paths and is not added to `legacy`, a role or RLS change so the definer function sees fewer `profiles` rows, a path stored with a different prefix) deletes real ID images in bulk within the hour, irreversibly. Today the logic matches the code I read, but nothing stops a bad run.
Fix: (a) a circuit breaker in the Edge Function: if one run lists more than, say, 50 files for `no_account` plus `no_row`, or more than 10 percent of the bucket, delete nothing, log the counts and notify admins; (b) a `dry_run` mode (body `{"dry_run":true}`) that returns counts only, used for the first runs on the test project and after every migration that touches `verification` paths; (c) a comment in `svc_verification_sweep_list` that every new column holding a `verification` path must be added to `legacy`.

## Low

- **LA1. Masking can push a note or reason over 300 characters and fail the action.** `admin_review_document` checks `char_length(p_note) > 300` (line 710) before the guard masks it (line 308); `admin_end_check` masks the reason (line 754) and `person_check_log.reason` allows 300. The 15-character replacement text for a 5-digit run makes the text longer, so a 295-character note fails with a constraint error. Fix: truncate after masking (`left(private.mask_digit_runs(x), 300)`), or lower the input limit to 250.
- **LA2. `mask_digit_runs` is easy to step around and over-masks.** The pattern on line 111 misses digits split by commas, underscores, colons or letters (for example the letter O written for zero) and hides dates and phone numbers. Acceptable for admin notes, which are a convenience, not a control. Add comma, underscore and colon to the class; do not rely on it for anything else. The owner-written `title` for kind `other` is not masked at all.
- **LA3. `document_opened` is logged only if the admin screen calls it.** The existing storage select policy (`20261012000200_guides.sql` line 154) lets any `aal2` admin sign any `verification` object directly, so the log is advisory. Acceptable for A; say so in the admin procedure, and check in the web change that the 60-second link (L1) is made only after `admin_log_document_opened` returns. The link length and `download` option are not in the code of A, so L1 is not yet verifiable.
- **LA4. Waiting documents are kept with no time limit.** The sweep never touches `waiting` rows (correct for M1), but an upload that is never reviewed stays forever. Add a service level for the review queue (operations) or a long retention for `waiting` (legal to set).
- **LA5. Sweep secret strength is not enforced.** `verification-sweep` accepts any non-empty `VERIFICATION_SWEEP_SECRET`. Refuse to run (503) if it is shorter than 32 characters. Because the endpoint can only trigger the deletions the database already lists, and the compare is constant-time, a shared secret is enough protection with `--no-verify-jwt`, provided the MA3 brake exists. Repeated calls cost only database scans.
- **LA6. No `supabase/config.toml` pins `verify_jwt` per function.** The deploy flags live only in comments. If `verification-sweep` is deployed with the JWT check on, the gateway rejects the Vault secret and the sweep silently never runs. Add `verify_jwt = false` for `verification-sweep` and `true` for `identifiers`, and a monitoring check that the sweep ran in the last two hours.
- **LA7. The sweep marks every name in a batch as removed** (`verification-sweep/index.ts` line 57), including names the Storage API did not confirm. Self-healing (the retention rule lists the file again while it exists), but pass only the confirmed names to `svc_verification_sweep_mark` so `removed_at` is true when written.
- **LA8. Rate limits are read-then-write races** (lines 836-840 and 940-942). Parallel requests can pass the count together. A per-actor `pg_advisory_xact_lock(hashtext(p_actor::text))` fixes it.
- **LA9. CORS default is only `https://kwetuly.com`.** The www host, Vercel previews and localhost will fail in the browser until `IDENTIFIERS_ALLOWED_ORIGINS` is set. Not a security issue (the bearer token is the access control, and browsers do not send it automatically, so no CSRF), but set it explicitly per project and never to `*`.
- **LA10. Legacy guide and business papers stay deletable and replaceable by their owners** (comment at line 229): M1 is fixed only for `person_documents`. Covered by L8 (move them into `person_documents`).

## Checked and found fine

- **H2:** a server-side sweep exists (pg_cron hourly via Vault, service role Edge Function, Storage API deletes, `removed_at` set, rows and dates kept). `path` is unique; index on `(review_state, reviewed_at)`. Deleted accounts (app or dashboard), files with no row after 24 hours, withdrawn, rejected (30 days) and accepted (90 days) files are covered; legacy paths in `guide_private` and `provider_private` match the `{user_id}/...` names that the web and mobile upload code writes. See MA3 for the missing brake.
- **M1:** owner delete policy replaced (only no row or `withdrawn`); there is no update policy on the `verification` bucket, so `upsert` and `move` cannot overwrite; insert refuses a path that already has a row; `path` must be exactly `{user_id}/{id}.{jpg|jpeg|png|webp|pdf}` by a check constraint. Account deletion still works: the client removes of protected files fail quietly and the sweep removes them once the profile is gone.
- **M2:** no owner update or delete policy or grant on `person_documents`; `withdraw_my_document` acts only on the waiting rows of the caller and sets only `review_state`; the insert guard forces `waiting`, null review fields, `uploaded_at` and `consented_at`, and checks provider ownership and file existence (but see MA1 for admins). The column insert grant leaves the review columns out.
- **M3:** each cipher is: 1 version byte, then a 12-byte nonce, then the AES-256-GCM ciphertext, then the 16-byte tag. The nonce comes from `crypto.getRandomValues` for every encryption and is never derived. AAD is `"{subject id}|{field}"` on both encrypt and decrypt, with the provider id as subject for `business_tin`. Keys are versioned, 32 bytes enforced, non-extractable, active version required. The HMAC version is stored beside each hash. Normalisation (NFKC, upper case, spaces, dashes and dots removed) happens before HMAC and encryption; the passport HMAC covers field, country and number, NIDA covers field and number. Decryption fails with one generic error. SQL checks that the version byte equals `p_key_version`. The version byte is not in the AAD, but changing it only selects another key and fails the tag.
- **M4:** one Edge Function. `auth.getUser(token)` verifies the token with the Auth server (index.ts line 94) before `aalOf` reads the aal claim of that same token (line 153). Owner writes use the id of the caller, never a body `user_id`; business TIN ownership is checked in SQL; a full read needs `aal2`, `profiles.role = 'admin'` read from the database, and a 5-300 character reason. `Cache-Control: no-store` and `nosniff` are set; no body, number, cipher or token is logged; errors are short codes; keys and service role live only in Edge secrets. Write limit 10 per 24 hours, read limit 20 per hour (alert broken, MA2).
- **M5:** `identifier_viewed` is inserted in the same transaction that returns the cipher, before the Edge Function decrypts; `identifier_set` and `identifier_cleared` carry the verified actor; `document_opened` exists and is written by `admin_log_document_opened`.
- **M11:** check methods are only `nida_card` and `passport_page`; a typed number is never a check; passport images are refused by a check constraint; `notice_version` and `consented_at` are on documents and identifiers; retention periods are implemented and labelled as proposals.
- **L4:** accept plus check is one function and one transaction, self-review refused. **L5:** 30-document cap (bypassable by admins, MA1). **L6:** `person_check_log.user_id` is `on delete set null` and `actor` has no foreign key; test 7 checks it.
- **RLS:** enabled on all five new tables. `person_documents` and `person_document_checks`: owner reads own, `aal2` admin reads all, no client write except the column-limited insert. `person_check_log`: `aal2` admins read only. `person_identifiers` and `business_identifiers`: no policy and no client grant; owners see only last 3, country and date through `my_identifiers()`; admins see masked values and the duplicate flag through functions that check `private.is_admin()`.
- **Grants:** every new public function revokes `public, anon` (and `authenticated` for the `svc_` functions, granted only to `service_role`), which also undoes the Supabase default execute grants. Private helpers are revoked from `public`; only those that storage policies and the caller-run guard need are granted to `authenticated`; `retention_days`, the trigger functions and `run_verification_sweep` have no client grant. The `private` schema is not exposed through the API.
- **SECURITY DEFINER:** every one has `set search_path = ''` and schema-qualified names. `withdraw_my_document` acts on `auth.uid()` only; admin functions check `is_admin()` first; `admin_end_check` needs a 5-300 character reason; `svc_identifier_set` requires actor equal to subject, onboarded, a known field, provider ownership and the version byte; `svc_identifier_cipher_for_read` re-checks role and reason (its `p_actor_aal` is supplied by the Edge Function, so the real aal check is there; acceptable because only `service_role` can call it); the sweep list caps `p_limit` at 1000.
- **Secrets:** none in code; `supabase/functions/.env` is git-ignored; `.env.example` holds names only; sweep URL and key are in Vault.
