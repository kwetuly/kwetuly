# Technical design: 2026-11-24 proposal list, roles and profiles, and the 2026-11-26 marketplace and uploads

Author: tech-lead. Date: 2026-11-24, section 9 added 2026-11-26. Status: design only, no feature code yet.
Base: branch `claude/reservations` at `af1833a`. Board groups: "2026-11-24 Proposal list" (A1-A17, B1-B12) and "2026-11-24 Roles and profiles" (RP1-RP12). Walter approved every item (decisions 1-12, R1-R15, and the changes in the 2026-11-24 chat). The board is owned by chief-of-staff and is not edited here.

Ground rules for every slice below:
- Every new table has row level security on, with policies in the same migration. Guard triggers stop users from setting admin-only fields (pattern: `public.guard_provider_admin_fields`, `public.guard_guide_package`). `security definer` only for narrow lookups, with `set search_path = ''`, and execute revoked from `public`/`anon` unless needed.
- New migrations come after `20261123000000_business_chat.sql` (the reservations migrations 20261122200000, 20261122300000 and 20261123000000 are not on live yet). Each migration stays under about 60 KB; tests go in `supabase/checks/<name>_tests.sql`, never inside the migration, so a paste stays under the editor's about 95 KB limit.
- Walter pastes all live SQL himself. Nothing in this design changes the live project.
- Texts: traveller texts in all 7 languages; guide, crew and owner texts in English and Kiswahili (Kiswahili for `sw`, English for the rest, like `linkCheckText`). All copy follows `docs/brand/voice.md`. Kiswahili drafts are checked by localization and Walter.
- Brand: green `#1D951A` for actions, gold `#ffb627`, grey `#7F7F7F`, 5px corners, no all caps, no arrows on buttons (this matters for "reorder" controls: use words such as "Move earlier", "Make main photo", not arrow icons).
- No invented facts or prices. Prices come from Walter (/admin/prices), the guide's or seller's own entry, or an official source named with a date.
- Before a slice is done: `npx tsc --noEmit -p .` in `apps/web` and `apps/mobile`, `npx expo lint` in `apps/mobile`, `npm test --workspace packages/shared`; after a migration on a test project, the security advisors.

## 2. Feature switches (the backbone for everything else)

### 2.1 Shape
Keep the existing mechanism; do not add a second one.
- Row: `site_settings` key `feature.<id>`, value `{"on": true|false, "legal": "pending"|"cleared"|"none", "legal_checked_on": "YYYY-MM-DD"|null, "team_only": false}`. The current shape check allows extra keys; the new migration tightens it so `legal` and `team_only`, when present, have the right type.
- The list of features, their names (English for Walter), their part (A, B, role, service, profile, marketplace, existing) and the legal question text live in code: `packages/shared/src/features.ts` (`FEATURES: { id, part, name, legalQuestion | null, boardRef }[]`). The question text is not stored in the database, so a code review sees every change to it. A test checks every id matches the SQL pattern and that every id in `FEATURES` is seeded by a migration.
- `private.feature_on(id)` stays as it is (fail closed). New `private.feature_visible(id)` = `feature_on(id) or (team_only and is_admin())`. Policies that hide data use `feature_on`; the admin "team preview" uses `feature_visible`.
- A switch hides screens and refuses writes; it never deletes data. Server rules that matter (for example, crew verification charging, marketplace checkout) also check `feature_on` inside the database function, not only in the screen.

### 2.2 Walter's decision and one exception
All switches start ON (Walter, 2026-11-24). Two exceptions I recommend, both need Walter's yes:
1. `feature.payments_live` stays OFF. It is the money gate; the payments code also refuses live keys until registration. Switching it on does nothing useful today and is dangerous.
2. `feature.save_to_travel` goes OFF. Walter's B5 decision is "instalments only, no save-to-travel"; the row exists and is ON with no code.

### 2.3 Server rules
- Migration `20261126000000_feature_switch_admin.sql`:
  - tightens `site_settings_feature_shape` (adds the optional keys);
  - seeds the new rows (list in 2.5) with `on: true, legal: 'pending'` where the board names a legal question, else `legal: 'none'`; existing rows get `legal` added without changing `on` (update with `value || jsonb_build_object(...)`);
  - `private.feature_visible(text)`;
  - `private.feature_switch_log` (append-only: key, old value, new value, changed_by, changed_at), filled by an `after update or insert` trigger on `site_settings` for `feature.%` keys; admins read it through `public.admin_feature_log(p_limit)`;
  - `public.admin_set_feature(p_id text, p_on boolean, p_legal text, p_legal_checked_on date, p_team_only boolean)`: security invoker, checks `private.is_admin()` (two-step session), refuses unknown ids (row must exist), writes the row. No delete path.
- Web reads: `apps/web/src/lib/features.ts` `getFeatures()` with `'use cache'` and `cacheTag('features')`; `featureOn(id)`; the admin action calls `revalidateTag('features')`. App reads: `apps/mobile/src/lib/features.ts` with React Query (stale time 5 minutes, kept offline).

### 2.4 Screens
- Web `/[lang]/admin/features`: one list grouped by part. Each row: name, board ref, on/off toggle, "Legal check pending" grey chip (or green "Legal checked on [date]"), the legal question in full, "Team only" toggle, last change (who, when). Filter: "Legal pending only". English only (admin).

## 4. Roles, sign-up and documents

### 4.1 Account types
- `profiles.role`: traveller, guide, provider (business), plus `crew` (new). Crew design follows `docs/team/design-crew-and-trip-management-2026-11.md` A.2: `crew_members.roles job_role[]` (porter, cook, camp_crew, driver, assistant_guide, other with `role_title`). A crew account may later add a guide profile.
- Guide kinds: `guides.guide_kinds` (mountain, safari, driver_guide, cultural; cultural covers city and village). `driver_guide` shows publicly as "Driver guide" only when `private.is_driver_guide()` is true; otherwise the guide's own "I drive guests" shows grey "Stated by the guide". Transfers stay off (B7).
- Services on a guide profile (not accounts): consultant = the existing paid call (`calls`), concierge = existing `personal_host` package kind with a visible "Offer VIP hosting" switch in step 2 and on the dashboard, trip runner, photographer, translator. Each is a `guide_services` row, admin-approved, behind its own switch.
- Hotel representative: a `provider_staff` seat invited by the owner, removable by the owner; no public profile.

### 4.2 Crew verification through guides
1. The guide creates an invite with a role on "My team" (web and app). The code is shown once with a WhatsApp share text; stored hashed; 1 use; expires in 14 days; at most 20 open invites per guide (guard).
2. The crew member signs up with it (4 steps, Kiswahili first): (1) name, phone, role(s), date of birth (refused under 18); (2) NIDA upload (`identity`) and the NGO porter ID (`porter_id`) into `person_documents`; (3) park rules acceptance (placeholder until legal); (4) photo and done. Big buttons, one question per screen on the phone, saves after each step so a dropped connection loses nothing.
3. The invite creates a `crew_vouches` row (guide, crew, vouched_at). Walter (admin) checks the documents and approves the person; the invite never approves anyone.
4. `guide_team_members` insert guard: crew must have an accepted `identity` document, be approved, be 18 or older, and have a live vouch. Guides cannot add anyone else.
5. Price: `price_list` row `crew_verification` per `priced_account_type`, amount null until Walter types it in /admin/prices. Charging is refused while `feature.crew_verification_fees` or `feature.payments_live` is off. Kwetuly never handles crew wages (B4 only through the partner's split, later).

### 4.3 Documents
One system: `person_documents`. Guide step 3 uploads there (ID, guide licence, driving licence, first aid, WFR, "other" with a title for courses, many files). The old `guide_private.*_document_path` columns stay read-only until Walter approves a copy script (S9 ships it as a reviewed SQL file, not applied). Public profile: green "Checked by Kwetuly on [date]" per accepted item from `guide_public_checks()`; everything typed in or not yet checked is grey "Stated by the guide". Files, ID numbers, phone and home address are never public.

### 4.4 Sign-up steps and the progress line
- Guides, 6 steps: about you (basics), what you do (work), documents, your trips, your page (story, cover, gallery, links), calls and booking link. Steps 1-4 required; the guide can submit for review after step 4.
- Crew, 4 steps (4.2). Hotel representative, 2 steps (accept the invite, name and phone).
- Park rules acceptance: a step for guides (inside step 4 "your trips") and crew (step 3). Text is a placeholder that says the rules are being prepared; acceptance records the version so a later version asks again.
- Shared helper `stepProgress(done: boolean[], required: number)` returns finished, total, left, requiredLeft. Text keys (draft, localization to check):
  - en: "You have finished {n} of {total}. {left} more steps to finish." / one left: "1 more step to finish." / none: "All steps finished."
  - sw: "Umemaliza hatua {n} kati ya {total}. Zimebaki hatua {left}." / "Imebaki hatua 1." / "Umemaliza hatua zote."
- The bar uses `role="progressbar"` with `aria-valuenow`, green fill, 5px corners.

The catalogue plan in `docs/tech/post-launch-catalogue-lessons-payments-plan.md` section 1.4 is the base; this extends it for guides as sellers, rentals, variants and specifications.

**Data (`20261127000300_marketplace_listings.sql`).**
- `listings.provider_id` becomes nullable; add `guide_id uuid` (fk guides, on delete cascade); check exactly one seller. Guides sell gear (for example to other guides).
- `pillar` and `region` optional (region falls back to the seller's base region); `category` from a fixed list in `packages/shared/src/marketplace.ts` (outdoor gear, camping, clothing, curios, art, jewellery, books and maps, other); a check in SQL mirrors it.
- `listing_type` ('sell', 'rent'); `condition` ('new', 'used'); `condition_note` (max 300); `brand` (max 60); `specs jsonb` (array of `{key, value}`, at most 20, each up to 40/120 chars, checked by a function); `stock` int null (null = "ask the seller") or `availability` for rentals through `availability_blocks` (A8, `marketplace_rentals` switch).
- Prices: `price_tzs`, `price_usd` (either or both; the seller's own), rentals `price_per_day_tzs/usd` and `deposit_note` (max 200, text only: Kwetuly holds no deposit). Local currency estimate from S10.
- `pickup` boolean, `delivery` boolean, `delivery_note`.
- Review: `status` with the `package_status` type (draft, pending, approved, rejected), `review_note`, `reviewed_at` (admin-only); `is_published` = the seller's own show/hide. Editing title, description, photos, price, condition, specs or category on an approved item sends it back to pending (copy of `guard_guide_package`).

- Limits: 100 items per seller (guard), seller must be approved and onboarded; Kwetuly Shop row refused for non-admins.
- Policies replace F1: public reads `status = 'approved' and is_published` with an approved seller; owners read and write their own; admins all. Sample sellers' items keep the sample label.
- `leads.listing_id`: `private.lead_target_ok` checks the item belongs to the same seller and is approved; the enquiry message records title and price at that moment.

### 9.2 One upload system

**Field spec in `packages/shared/src/uploads.ts`** (one source for web, app and the SQL checks; a test compares them):

| Field | Count | Types in | Output | Max size stored | Crop | Bucket | Shown |
| --- | --- | --- | --- | --- | --- | --- | --- |
| avatar | 1 | jpeg, png, webp, heic (app) | WebP 800 px + 200 px thumb | 1 MB | 1:1 fixed | media | at once |
| cover | 1 | as above | WebP 2000x667 + 800 px thumb | 2 MB | 3:1 fixed | media | at once, then checked |
| gallery | 12 | as above | WebP 1600 px + 400 px thumb | 2 MB | free | media | at once, then checked |
| product | 10 | as above | WebP 1600 px + 400 px thumb | 2 MB | free (square suggested) | media-pending, copied to media on approval | after approval |
| document | many (20 open per person) | jpeg, png, webp, pdf | images WebP 2400 px; PDF unchanged | 15 MB | none | verification (private) | never public |

**Client (web, `media-field.tsx`).**
- Pick by button, drag-and-drop, or paste; multiple files up to the field's remaining count.
- Each image is decoded with `createImageBitmap` (EXIF rotation applied), redrawn on a canvas, resized, and encoded to WebP (`canvas.toBlob(..., 'image/webp', 0.8)`); if the browser returns another type (older Safari), fall back to JPEG and record the real type. Redrawing drops EXIF and GPS. A thumbnail is made the same way. If decoding fails (for example HEIC outside Safari), the file is refused with a clear message; the original is never uploaded.
- Fixed-aspect crop for avatar and cover: a small dialog with drag and zoom (pointer and keyboard), no heavy library.
- Upload queue: each file has a progress bar (XHR `upload.onprogress` to a signed upload URL), states waiting, uploading, done, failed, with "Try again" per file; uploads run two at a time; the form cannot be saved while one is uploading (as `DirectUpload` does today).
- Reorder: drag on desktop, and buttons "Move earlier", "Move later", "Make main photo" for touch and keyboard (no arrow icons).
- Remove: asks once, then deletes.

**Client (app, `media-field.tsx`).** expo-image-picker (multiple selection, limit = remaining count), `cleanPhoto` extended to WebP and a thumbnail (`SaveFormat.WEBP`), upload with progress through expo-file-system's upload task (check the current SDK docs as `apps/mobile/AGENTS.md` asks), retry per file. Cover crop: iOS's picker only crops square, so the app uses its own fixed-aspect crop step (ImageManipulator `crop`) for cover; avatar uses the picker's square crop. Reorder with "Move earlier/later" and "Make main photo".

**Server rules (`20261126000100_media_uploads.sql`).**
- `public.media`: id, owner_id, subject_kind (guide, provider, listing), subject_id, field (avatar, cover, gallery, product), path, thumb_path, mime, bytes, width, height, placeholder colour (hex), sort, is_main, state (uploading, live, pending, checked, removed), consent_version, consented_at, removed_reason, created_at. Guard: counts per field from the spec, owner must own the subject, admin-only for checked/removed, `path` must match `{owner_id}/{id}.(webp|jpg)`.
- Flow: server action `startUpload(field, subject)` inserts the row (state uploading) and returns a signed upload URL for exactly that path; `finishUpload(id, width, height)` calls `private.media_object_ok(id)`, which reads `storage.objects` metadata (size, mimetype) and refuses wrong type or size, then sets the state (`live` for avatar/cover/gallery, `pending` for product). Width and height are client-reported but bounded (1 to 4000) and only used for layout.
- Buckets: `media` public, `file_size_limit` 2 MB, `allowed_mime_types` webp and jpeg; `media-pending` private, same limits; `verification` unchanged (15 MB, pdf allowed). Storage insert policies: folder = `auth.uid()`, name matches the media row in state uploading owned by the caller. Delete: owner or admin. Admins may insert into `media` (for copying approved product photos).
- Removing or rejecting a photo deletes the storage object (public URLs stop working once the CDN entry expires) and keeps the row as `removed` for the audit trail.
- Sweep: `private.media_sweep()` deletes `uploading` rows and their objects after 24 hours, run from the existing cron pattern.
- Account deletion: `delete_my_account` path must remove the person's `media` objects in both buckets (add to the deletion cleanup; check against `20261016001200_account_deletion_cleanup.sql`).

**No layout shift.** Screens read width, height and the placeholder colour from `media` and render a box with that aspect ratio and colour before the image loads (`next/image` with width and height on the web, `expo-image` with `placeholder` on the app). Thumbnails are used in grids; the full image only in the viewer. This avoids Supabase image transformations (paid plan) and keeps pages light on roaming data.

## 10. Risks

1. **Switches ON while legal is pending.** Walter's choice means Part B screens (tipping numbers, insurance partner, jobs fees, trip runner) are public before the advocate answers. Mitigation: every legally open item shows nothing that charges money (payments_live off), and the admin page lets Walter turn any one off in a click. I recommend using "Team only" for Part B until each answer comes back. Walter decides.
2. **Public photos before checking.** "Shown at once, then checked" means a bad photo is public for hours. Mitigation: report button, admin queue sorted oldest first, consent tick, delete-on-remove. A 24-hour check target for operations-manager.
3. **Personal data of crew.** NIDA images, dates of birth and porter IDs are sensitive (PDPA 2022). Private bucket only, minimal fields, deletion path, crew pages not public. Needs security-reviewer and legal's notice text before crew sign-up goes live.
4. **Guide-made invites as a spam or impersonation path.** Hashed, single use, 14-day expiry, 20 open per guide, Walter approves each person.
5. **Marketplace goods.** Wildlife products, gemstones without papers, counterfeit gear. Admin review per item, banned list from legal, report button, no checkout.
6. **Exchange rates.** A wrong or stale rate looks like a Kwetuly price. Always "about", always the named source and date; hide the estimate when the rate is older than 7 days.
7. **Web offline cache.** A service worker can serve stale or private pages. Cache only public pages and the person's own trip data, clear on sign-out, version the cache.
8. **WebP on old browsers and iOS crop.** Handled by the JPEG fallback and the app's own crop step; qa-tester tests on an older Android and an iPhone.
9. **Migration size and order.** The reservations migrations are not live yet; every new file assumes they are. If Walter applies the new ones first, `price_list` changes in S10 and S16a fail. Order is stated in each file's header.
10. **Wave 1 merge order.** S2 first, then S1, S3, S4, S5 in any order; the shared index files need a trivial merge.
